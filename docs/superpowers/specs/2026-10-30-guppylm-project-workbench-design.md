# GuppyLM 核心综合项目工作台设计

- 日期：2026-10-30
- 状态：已批准并进入验收
- 规模：单页面增量改造
- 所属课程：《从零手写大模型》`llm-a1`

## 1. 意图

为 GuppyLM 建立一个独立的项目工作台，而不是在 A1 课程中继续追加长篇教程。

学习者应当通过八个可操作、可验收的任务，把 A1 学到的分词器、Transformer、自回归训练、文本生成和模型导出串成一次完整工程闭环。页面需要同时回答三个问题：

1. 这个设计为什么成立？
2. 源码实际上做了什么？
3. 我怎样亲手验证，而不是只看别人总结？

内容风格要详细、通俗、有节奏，避免术语堆叠和连续大段文字。复杂概念用图、对比、短代码、运行结果和可切换的实验观察来承载。

## 2. 课程归属

推荐作为 `llm-a1` 的收官核心项目，不新增课程。

理由：

- GuppyLM 从 BPE 分词、Transformer 前向、自回归训练一直覆盖到 ONNX 浏览器部署，与 A1 的“从文本到 GPT”主线一致。
- A2 负责交叉熵、AdamW、学习率调度等训练理论深化；本项目在任务 5 中只建立必要直觉，并链接 A2。
- B3 负责 KV Cache、量化、生产部署等工程深化；本项目在任务 7 中只完成 ONNX 量化与浏览器推理闭环，并链接 B3。
- 独立页面能承载八个任务和验收交互，又不会把 A1 的课程章节列表拉成长篇附录。

入口：

- 新路由：`/project/guppylm`
- A1 课程页 hero 区增加“核心综合项目：GuppyLM”入口卡片或按钮
- 项目页提供返回 `llm-a1` 的链接

## 3. 备选方案与取舍

### 方案 A：嵌入 A1 章节

优点是路由和导航改动最少；缺点是八个任务会变成很长的单章内容，源码、实验和验收状态难以分层，容易重新落回“几十页教程”。

### 方案 B：独立项目工作台（已选）

新增 `/project/guppylm`，以任务切换器一次聚焦一个任务，每项统一包含原理、源码、实验、思考与验收。页面复用现有站点壳层和视觉变量，同时用“水族实验记录”作为局部视觉主题。

优点是独立、可操作、可验收，移动端也能保持清晰层级；代价是需要新增页面、内容模型和项目级进度状态。

### 方案 C：工作台内嵌完整 ONNX 推理

优点是可直接在页面里改 temperature 和 top-k；缺点是需要加载约 10 MB 模型、WASM 运行时和额外静态资源，首屏与移动端成本高，且会把教学重点转移到推理运行时集成。

本项目选择 B，提供官方浏览器 Demo 链接和固定 seed 的真实结果；交互重点放在任务导航、概念演示、参数对照和验收，而不是重复部署一个模型。

## 4. 目标与非目标

### 目标

- 八个任务都有明确目标、预计时间、难度和完成证据。
- 每个任务都区分“原理解释 / 源码解析 / 实验验证 / 拓展实践”。
- 关键内容来自固定提交的真实源码和实际运行结果，不编造训练曲线。
- 通过任务切换、图示、代码块、结果卡和验收清单控制认知负荷。
- 桌面端支持快速跳转和连续阅读；移动端保持单列、可点击、无横向溢出。
- 项目进度和任务验收状态可保存，刷新后不丢失。
- 页面与现有知序学院的课程、按钮、字体、色彩和可访问性规范一致。

### 非目标

- 不在页面内复制完整 GuppyLM 仓库或 10 MB ONNX 文件。
- 不承诺浏览器内完成 10,000 步训练。
- 不把官方低困惑度直接解释为强泛化能力。
- 不新增后端接口、数据库表或新依赖。
- 不修改 A1 的大段课程正文。
- 不制作完整的八篇长教程。

### 失败条件

- 页面只是八段连续 Markdown，没有任务聚焦和验收。
- 用“测试集 PPL 很低”掩盖 77.3% 的训练/测试精确重叠。
- 伪造训练日志、损失曲线或用户运行必然一致的生成文本。
- 为了视觉效果牺牲可读性、键盘操作或移动端布局。

## 5. 已核实事实

### 仓库与模型

- 仓库：`arman-bd/guppylm`
- 固定提交：`a30df3091cff73a259ce581dd8439271084bca40`
- 参数量：`8,726,016`
- 词表配置：`4096`
- 最大序列长度：`128`
- 隐藏维度：`384`
- Transformer Block：`6`
- 注意力头：`6`
- FFN 隐层：`768`
- dropout：`0.1`
- 特殊 token：pad `0`、bos/im_start `1`、eos/im_end `2`

### 数据与真实评估

- 官方数据：train `57,000`，test `3,000`，`60` 个类别。
- train 中唯一 `(input, output)` 对：`15,613`
- test 中唯一 `(input, output)` 对：`2,050`
- test 与 train 精确重叠：`2,320 / 3,000`，占 `77.3%`
- 官方 ONNX 在全部 test 上：loss `0.407009`，PPL `1.502318`
- 重叠样本：loss `0.360079`，PPL `1.433443`
- 非重叠样本：loss `0.539113`，PPL `1.714486`
- 均匀猜测基线：`ln(4096) = 8.3178`

### 分词器

- 实际下载的 `docs/tokenizer.json` 词表大小：`2,418`
- BPE merges：`2,352`
- 训练请求 `vocab_size=4096`，但语料只产生 2,418 个词表项。
- 模型 embedding 仍按 4,096 分配，后部 ID 实际未使用。
- `hi guppy` 编码为 `[779, 278]`，tokens 为 `['hi', 'Ġguppy']`。

## 7. 八个任务的内容规格

### 任务 1：认识项目

目标：说清 GuppyLM 要解决什么问题、由哪些模块组成、代码从哪里开始读、需要什么环境。

原理：

- 用“从一句话到一条鱼回复”的端到端流水线解释项目，而不是先罗列文件。
- 强调这是一个“小模型全流程教学项目”，不是追求通用能力的生产模型。

源码：

- `README.md`
- `guppylm/config.py`
- 根目录与 `guppylm/`、`tools/`、`docs/`、notebooks 的职责
- 参数量 8,726,016 的来源

实验：

- 克隆并创建 Python 环境
- 打印配置和参数量
- 运行一次最小前向：`(2, 32)` 输入得到 `(2, 32, 4096)` logits
- 验证 embedding 与输出层权重绑定

拓展：

- 画出自己理解的数据流，并标出每层张量形状。

验收：

- 能解释四个核心目录各自的职责
- 能复现前向输出形状
- 能指出词表配置大小与实际分词器大小的区别

### 任务 2：理解训练数据

目标：理解 `input/output/category` 数据结构，分清名义测试集和真正未见样本。

原理：

- 训练样本是一条鱼对用户话语的短回复；类别是话题标签，不是输入特征。
- 训练集用于更新参数，测试集用于估计未见数据表现。
- 精确重复、模板重复和分词器训练污染都会让测试结果偏乐观。

源码：

- `generate_data.py`：合成 60K 对话后随机划分
- `prepare_data.py`：在 train + eval 全部文本上训练分词器
- `dataset.py`：读取 parquet、拼接 ChatML、编码

实验：

- 读取官方 parquet，打印字段、行数、类别分布
- 用 `(input, output)` 精确匹配统计重叠
- 对重叠与非重叠样本分别计算 loss/PPL
- 观察 77.3% 重叠与 1.50 / 1.43 / 1.71 的差异

拓展：

- 设计按模板去重、按类别留出或按生成种子分组的更干净划分。
- 讨论为什么“随机切分”不足以保证泛化评估。

验收：

- 能解释 train/test 的职责
- 能复现重叠率或读懂统计脚本
- 能说明为什么低 PPL 不能直接证明泛化强

### 任务 3：训练分词器

目标：理解 ByteLevel BPE 如何把文本变成 token ID，以及 4,096 与 2,418 的差异。

原理：

- BPE 从字符/字节开始，反复合并高频相邻片段。
- token 不是“词”，常见词可能是一个 token，生僻词会被拆成多个。
- 词表越大，序列越短，但 embedding 和输出层越大。

源码：

- `prepare_data.py` 中的 `ByteLevelBPETokenizer`、`BpeTrainer`
- 特殊 token 的顺序与 ID
- `dataset.py` 中 tokenizer 的使用

实验：

- 训练或加载 `docs/tokenizer.json`
- 打印词表大小、merges 数量、特殊 token
- 对 `hi guppy` 编码并查看 token 文本
- 对完整 ChatML prompt 编码，观察 10 个 token
- 对比配置 4,096 与实际 2,418，解释未使用 embedding 行

拓展：

- 改小 `vocab_size` 或换一批语料，比较序列长度与模型参数量。

验收：

- 能手工解释一次 BPE 合并
- 能说明特殊 token 的作用
- 能解释为什么词表配置和实际 tokenizer 大小可以不同

### 任务 4：阅读 Transformer

目标：逐步解释 token embedding、位置嵌入、多头注意力、FFN、残差和 LayerNorm。

原理：

- token embedding 回答“这个 token 是谁”，位置嵌入回答“它在哪里”。
- 多头注意力让不同头从不同关系角度交换信息。
- 残差保留原信息，LayerNorm 稳定数值；Pre-LN 让深层训练更稳定。
- FFN 对每个位置独立做非线性变换。

源码：

- `model.py` 的 `Attention`、`FeedForward`、`Block`、`GuppyLM`
- 每个 Block 参数量约 1,183,872，六层合计 7,103,232
- 权重绑定与最终 logits 计算

实验：

- 用可切换的 Block 图查看每一步张量形状
- 输入 `(2, 32)` token，观察 attention mask、logits 与权重绑定
- 修改层数或宽度，打印参数变化

拓展：

- 把 ReLU FFN 换成 GELU，或把绝对位置嵌入换成 RoPE，记录需要改哪些接口。

验收：

- 能用自己的话解释 Q/K/V
- 能指出残差和 LayerNorm 在代码中的位置
- 能根据配置手算或脚本验证参数量

### 任务 5：理解训练过程

目标：理解自回归 next-token prediction、交叉熵、AdamW、warmup 与余弦学习率。

原理：

- 输入序列左移一位，目标序列右移一位。
- 每个位置都在预测下一个 token；交叉熵衡量正确 token 的概率有多低。
- AdamW 分别维护一阶、二阶矩并做解耦权重衰减。
- warmup 避免早期大步长破坏参数，余弦衰减让后期更新更细。

源码：

- `dataset.py` 的 `x = ids[:-1]`、`y = ids[1:]`
- `model.py` 的 cross entropy
- `train.py` 的 AdamW、betas、weight decay、warmup、cosine、grad clip、AMP

实验：

- 展示一个短序列的 x/y 位移表
- 打印第 0、100、200、1000、5000、9999 步学习率
- 用已导出的 ONNX 结果解释 loss 与 PPL 的换算
- 明确区分“理论配置”和“本次是否完整训练”

拓展：

- 只改 warmup 或学习率，设计一次短程对照实验，并预先写出判断标准。

验收：

- 能解释为什么 x 与 y 要错一位
- 能手算一个 next-token 损失例子
- 能说明 warmup 与余弦衰减各自解决什么问题

### 任务 6：运行模型推理

目标：观察生成结果，理解 temperature 与 top-k 如何改变概率分布和文本风格。

原理：

- 模型每步输出整个词表的 logits，采样后才得到一个 token。
- temperature 缩放 logits；低温更确定，高温更发散。
- top-k 只保留概率最高的 k 个候选，减少离谱 token。
- 高温 + 大 top-k 更自由，也更容易跑题。

源码：

- `model.py::generate`
- `inference.py::chat_completion`
- ChatML 模板、eos 停止与 `max_new_tokens`

实验：

- 固定 seed 42，分别运行三组 prompt × 三组参数
- 对比低、中、高温度的生成结果
- 观察 `are you hungry` 从直接回答到跑题的边界
- 提醒：不同运行时、设备和 seed 可能产生不同文本

拓展：

- 固定 prompt 与 seed，只改 temperature；或固定 temperature，只改 top-k。
- 设计一张“参数—多样性—稳定性”观察表。

验收：

- 能解释 temperature 和 top-k 的区别
- 能复现至少一组推理命令
- 能用证据说明高温为什么更发散

### 任务 7：导出并部署模型

目标：理解 PyTorch → ONNX → 动态量化 → ONNX Runtime Web/WASM 的完整链路。

原理：

- ONNX 把计算图导出为跨框架格式。
- 动态量化把权重压成更低比特，在推理时反量化；不是无损压缩。
- 浏览器通过 WASM 运行推理，无需 GPU 或后端服务。

源码：

- `tools/export_onnx.py`
- opset 17、动态 batch/seq
- `docs/index.html` 的 `onnxruntime-web 1.21.0`
- `docs/model.onnx` 的文件大小与 SHA256

实验：

- 运行导出脚本
- 检查 ONNX 输入输出和动态维度
- 对比 PyTorch 与 ONNX 在同一输入上的 logits/生成结果
- 打开官方 Demo，观察模型下载和浏览器推理

拓展：

- 比较量化前后文件大小、首 token 延迟和输出差异。
- 讨论动态量化的误差来源。

验收：

- 能画出部署链路
- 能说明动态 batch/seq 的意义
- 能解释量化为什么可能改变输出

### 任务 8：完成拓展实验

目标：改变数据、模型参数或序列长度，完成一次单变量对照实验并解释结果。

原理：

- 一次只改一个变量，预先定义观察指标，避免把随机波动当成因果。
- 参数量、计算量、序列长度、数据质量和评估泄漏都会影响结果。
- 小模型实验的价值在于理解机制，不是追求榜单分数。

源码：

- `config.py`
- `train.py`
- `generate_data.py`
- `tools/export_onnx.py`

实验：

- 参数对照：
  - baseline：8.73M
  - 3 层：5.17M
  - 8 层：11.09M
  - `d_model=256, FFN=512, heads=4`：4.24M
  - 序列 64：8.70M
  - 序列 256：8.78M
  - 3 层 + 序列 64：5.15M
- 数据实验：按模板去重、限制类别、改变回复长度
- 训练实验：短程 loss、生成稳定性、显存/耗时

拓展：

- 从“改数据、改参数、改序列长度”中选一个方向，写出假设、变量、控制量、指标和结论。

验收：

- 实验只改了一个主变量
- 有 baseline、指标和可复现命令
- 结论与证据一致，并写明局限

- 验收复选框可点击，进度写入 `localStorage`，键为 `knowledge-order:guppylm-project:v1`。
- “全部完成”只在八项任务均有验收证据时出现，不按打开页面自动完成。
- 代码块提供文件名、语言标签和复制按钮；复制失败有可访问提示。
- 思考题默认只显示问题，可展开提示或参考答案；避免学习者一上来就抄结论。
- 图表均为原生 HTML/CSS/SVG，不新增图形库。

## 10. 内容与真实性约束

- 所有代码路径、命令和结果标明来源提交。
- 训练配置写成“仓库配置”，不写成“本站已完整训练 10,000 步”。
- ONNX 评估写成“对官方 3,000 条测试样本的实测”。
- 推理文本写成“固定 seed 的示例”，不承诺逐字复现。

## 12. 已知风险

- 内容量较大，若全部同时渲染会重新变成长文；必须一次聚焦一个任务。
- 官方测试泄漏是负面结论，但也是本项目最有价值的学习点；表达要清楚、不羞辱仓库作者。
- 代码片段来自第三方仓库，需保留来源和固定提交链接。
- 本地存储只保存验收状态，不保存代码运行结果；页面要明确这一点。
- 当前工作区有大量用户未提交修改，只能增量新增或最小化修改，不能回滚无关文件。

## 13. 需要用户确认的决定

- 采用独立 `/project/guppylm` 工作台，而不是嵌入 A1 章节。
- 页面以“详细但不长文”的任务工作台呈现，八项任务一次聚焦一项。
- 不内嵌完整 ONNX，只链接官方 Demo，并提供真实实测结果。
- 将 77.3% 测试重叠与 4,096/2,418 词表差异作为核心教学材料。
