## 为什么需要采样

模型给出的是概率分布。**贪心解码**（每步取最大概率）虽然确定，但会导致：

- 输出呆板、重复；
- 容易陷入循环（如重复同一句话）。

生成质量与多样性需要权衡，因此引入了采样策略。

## 温度（Temperature）

对 logits 除以温度 T 后再 softmax：

```
p_i = softmax(logits_i / T)
```

| T | 效果 |
| --- | --- |
| T → 0 | 趋近贪心（最确定） |
| T = 1 | 原始分布 |
| T > 1 | 分布变平（更随机、更发散） |
| T < 1 | 分布变尖（更保守、更确定） |

```python
def softmax_with_temperature(logits, T=1.0):
    scaled = logits / T
    e = np.exp(scaled - np.max(scaled))
    return e / e.sum()
```

**实践建议**：事实性任务用 T=0~0.3；创意写作 T=0.7~1.0。

## Top-K 采样

只从概率最高的 K 个 token 中采样，其余置零后重新归一化。

```python
def top_k_filter(logits, k):
    kth = np.sort(logits)[-k]
    filtered = np.where(logits >= kth, logits, -np.inf)
    e = np.exp(filtered - np.max(filtered))
    return e / e.sum()
```

**问题**：K 是固定值。当分布很尖时（模型很确定），K=50 可能包含大量垃圾词；
当分布很平时，K=50 又可能删掉合理选项。

## Top-P（核采样 / Nucleus Sampling）

按概率从高到低累加，取累计概率刚好超过 P 的最小集合。

```python
def top_p_filter(probs, p=0.9):
    order = np.argsort(-probs)
    sorted_p = probs[order]
    cum = np.cumsum(sorted_p)
    cutoff = np.searchsorted(cum, p) + 1
    keep = order[:cutoff]
    mask = np.zeros_like(probs, dtype=bool)
    mask[keep] = True
    filtered = np.where(mask, probs, 0)
    return filtered / filtered.sum()
```

**优势**：候选集合**随分布自适应**——模型确定时集合小，模型犹豫时集合大。
这是 GPT-3、ChatGPT 等的主流配置（常见 p=0.9~0.95）。

## 训练不同阶段需要不同的学习率

- **初期**：参数随机初始化，梯度方向不可靠且量级大。直接用大学习率容易发散。
- **中期**：需要较大步长快速下降。
- **后期**：已接近最优，需要小步长精细调整，否则会在最优点附近震荡。

所以实践中都在**动态调整学习率**。

## Warmup：先小后大

前 N 步让学习率从 0（或很小的值）**线性增加到峰值**：

    if step < warmup_steps:
        lr = peak_lr * step / warmup_steps
    else:
        lr = 衰减策略(step)

**为什么需要 warmup**：

1. **Adam 的二阶矩方差估计在初期极不稳定**——v 基于极少的样本，
   √v 可能非常小，导致实际步长 `lr/√v` 巨大，容易一步跳飞。
2. **大 batch 训练时梯度方向在初期变化剧烈**，小步长有助于稳定。
3. **残差分支的激活值初期可能很大**，小学习率避免发散。

Transformer 原论文（Attention Is All You Need）就使用了 warmup：
`lr = d_model^(-0.5) · min(step^(-0.5), step · warmup_steps^(-1.5))`

**常见 warmup 长度**：总步数的 1%~5%（如 1000~2000 步）。

## 三种主流衰减策略

**1. 余弦衰减（Cosine Decay）—— 最常用**

    progress = (step - warmup) / (total - warmup)
    lr = min_lr + 0.5 * (peak_lr - min_lr) * (1 + cos(π * progress))

特点：前期缓降、中期快速下降、后期趋于平缓。
LLaMA、GPT-3 等都使用余弦衰减（通常带 min_lr，如峰值的 10%）。

**2. 线性衰减（Linear Decay）**

    lr = peak_lr * (1 - progress)

简单直接，T5、部分 BERT 变体使用。

**3. 逆平方根衰减（Inverse Square Root）**

    lr = peak_lr / sqrt(progress)

衰减快，适合长训练。原版 Transformer 用这个变体。

## 学习率调度曲线对比

| 策略 | 前期 | 中期 | 后期 | 适用 |
| --- | --- | --- | --- | --- |
| 常数 | 平 | 平 | 平 | 短训练、微调 |
| 阶梯衰减 | 平 | 突降 | 突降 | 传统 CNN（ResNet） |
| 余弦 | 缓降 | 快降 | 趋平 | **大模型预训练首选** |
| 线性 | 缓降 | 匀速 | 趋平 | 简单场景 |
| 逆平方根 | 快降 | 慢降 | 极慢 | 长训练 |

## 先算一笔账

训练一个 7B 模型（fp16），显存需求：

| 项目 | 大小 | 说明 |
| --- | --- | --- |
| 模型权重（fp16） | 14 GB | 7B × 2 字节 |
| 梯度（fp16） | 14 GB | 与权重同形状 |
| 优化器状态（Adam） | 56 GB | fp32 的 m + v 各 28GB |
| **小计（不含激活）** | **84 GB** | 已经超过 80GB 单卡 |
| 激活值（随 batch/序列长度增长） | 数十 GB | 反向传播要用 |

**结论**：7B 模型全参训练起步就要 100+ GB，单卡放不下。
必须把显存和计算分散到多张卡上——这就是分布式训练。

## 四种并行方式的分工

| 方式 | 切什么 | 解决什么 | 通信特点 |
| --- | --- | --- | --- |
| **数据并行 DP** | 切 batch | 训练速度（吞吐） | 每步同步梯度，量大 |
| **张量并行 TP** | 切单层内的矩阵 | 单层放不下 | 每层都通信，量最大 |
| **流水线并行 PP** | 切层（按深度） | 层数太多 | 只在层边界通信，气泡问题 |
| **序列并行 SP** | 切序列长度 | 长上下文激活爆 | 注意力内部通信 |

**实际大模型训练通常是三者组合**：
例如 70B 模型在 1024 卡上训练，可能是
**TP=8 × PP=8 × DP=16** 的 3D 并行。

## 数据并行（DP）：最直观

每张卡放一份**完整的模型**，各自处理不同的数据，然后同步梯度：

    # 每张卡
    loss = model(batch_i)
    loss.backward()               # 各自算梯度
    all_reduce(gradients)         # 所有卡梯度求平均
    optimizer.step()              # 更新后参数仍然一致

**优点**：实现简单，几乎线性加速。
**缺点**：每张卡都要放完整模型——**显存没有节省**，只解决了速度。

这就是为什么大模型不能只用 DP。

## 分布式数据并行（DDP）

PyTorch 的 `DistributedDataParallel` 相比老的 `DataParallel` 的关键改进：
**梯度同步与反向传播重叠**（bucket + async all-reduce）。

反向传播是逐层算梯度的，DDP 一边算一边把已完成的梯度桶发出去，
不等全部算完再同步——通信时间被计算时间掩盖。

## All-Reduce 是什么

所有卡把自己的数据发出去，最终每张卡都拿到**所有卡的归约结果**（如求和/平均）。

    ring all-reduce：每张卡只与左右邻居通信，
    N 张卡传输 2(N-1)/N 倍数据量，与卡数几乎无关

**关键认知**：all-reduce 的通信量与**参数量**成正比。
7B 模型 fp16 → 每步要同步 14GB 梯度。这就是 DP 的通信

## 张量并行（TP）：把一层劈开

以矩阵乘法 Y = XW 为例，W 形状 (d_in, d_out)。

**按列切 W**（Megatron 的 Column Parallel）：

    W = [W1 | W2]        # 每张卡存一半列
    Y1 = X @ W1, Y2 = X @ W2    # 各自算出一半输出
    # 列并行无需通信（输出天然分开）

**按行切 W**（Row Parallel）：

    W = [W1; W2]         # 按行切
    Y = X1 @ W1 + X2 @ W2       # 需要把部分和加起来 → all-reduce

**MLP 的标准切法**：第一个线性层按列切（无通信），第二个按行切（一次 all-reduce）。

    h = GELU(x @ W1)  →  W1 按列切，各卡算一部分 h
    y = h @ W2        →  W2 按行切，各卡算部分和，all-reduce 求和

**多头注意力的切法**：按 head 切。每个卡负责一部分 head，天然独立；
只有最后的输出投影需要 all-reduce。

**TP 的特点**：
- 通信量最大（每层都要 all-reduce）；
- 必须放在**同一节点内**（NVLink，带宽 ~600GB/s），跨节点以太网撑不住；
- 通常 TP ≤ 8（不超过单机 GPU 数）。

## 流水线并行（PP）：按层切

把模型的 L 层分成 P 段，每段放在一张卡上：

    卡1: layer 1-8   卡2: layer 9-16   卡3: layer 17-24   卡4: layer 25-32

数据依次流过，看起来很自然，但有个大问题：**气泡（bubble）**。

    # 朴素做法：同一时刻只有一张卡在工作
    卡1: [====]
    卡2:        [====]
    卡3:               [====]
    卡4:                      [====]
    → 利用率只有 1/4

**解决：微批次（micro-batch）流水**。把一个大 batch 切成 m 个小块，
让各卡交错执行：

    # 1F1B 调度（一前一后）
    卡1: F1 F2 F3 F4 B1 B2 B3 B4
    卡2:    F1 F2 F3 F4 B1 B2 B3 B4
    ...

气泡比例约 **(P-1)/m**（P=流水段数，m=微批次数）。
**m 越大，气泡越小**，但 micro-batch 太小会影响 GPU 效率。

**PP 的特点**：通信量最小（只在段边界传激活），可以跨节点；
但需精心调度微批次来减少气泡。

## 数据并行的显存浪费

DP 下每张卡都存一份完整的：权重 + 梯度 + 优化器状态。
**这些是完全冗余的**——N 张卡存了 N 份相同的东西。

**ZeRO（Zero Redundancy Optimizer）的思路**：把这些冗余切开，各卡只存 1/N。

<Diagram type="arch" name="kv-cache" />

## ZeRO 三个阶段

| 阶段 | 切什么 | 每卡显存（相对 DP） | 通信量 |
| --- | --- | --- | --- |
| **ZeRO-1** | 优化器状态 | 权重 + 梯度 + 优化器/N | 与 DP 相同 |
| **ZeRO-2** | + 梯度 | 权重 + 梯度/N + 优化器/N | 略增 |
| **ZeRO-3** | + 权重 | (权重 + 梯度 + 优化器)/N | 增 1.5 倍 |

以 7B 模型为例（DP=8）：

| 方式 | 每卡显存 | 说明 |
| --- | --- | --- |
| 纯 DP | 84 GB | 装不下 |
| ZeRO-1 | 14 + 14 + 7 = 35 GB | 优化器切 8 份 |
| ZeRO-2 | 14 + 1.75 + 7 = 22.75 GB | 梯度也切 |
| ZeRO-3 | (14+14+56)/8 = 10.5 GB | 全切 |

**ZeRO-3 是怎么做到的**：前向/反向时，用到哪一层就把那一层的权重从别的卡**取过来**（all-gather），
用完立刻释放。所以显存省了，但通信量增加。

## FSDP：PyTorch 官方的 ZeRO-3

`FullyShardedDataParallel` 是 PyTorch 对 ZeRO-3 的原生实现：

```python
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,   # 相当于 ZeRO-3
    # SHARD_GRAD_OP 相当于 ZeRO-2
    # NO_SHARD 相当于普通 DDP
    mixed_precision=MixedPrecision(param_dtype=torch.bfloat16),
    device_id=torch.cuda.current_device(),
)
```

**关键：FSDP 包装的粒度**。通常按 Transformer Block 包装（`auto_wrap_policy`），
这样 all-gather 是以 block 为单位，能在计算当前 block 时预取下一个。

## 三种精度的位分配

浮点数的格式是「1 位符号 + 指数位 + 尾数位」：

| 格式 | 符号 | 指数 | 尾数 | 动态范围 | 精度（有效数字） | 字节 |
| --- | --- | --- | --- | --- | --- | --- |
| **fp32** | 1 | 8 | 23 | ±3.4e38 | ~7 位十进制 | 4 |
| **fp16** | 1 | 5 | 10 | ±65504 | ~3 位十进制 | 2 |
| **bf16** | 1 | 8 | 7 | ±3.4e38 | ~2 位十进制 | 2 |

**关键观察**：
- fp16 与 bf16 **同为 2 字节**，省一半显存与带宽；
- 但两者的取舍方向**完全相反**：
  - fp16 尾数多（10 位）→ **精度高但范围窄**（超过 65504 就溢出）
  - bf16 指数多（8 位，与 fp32 相同）→ **范围大但精度低**

## 为什么大模型几乎都选 bf16

训练中最大的风险是**数值溢出**，而不是精度不够。典型场景：

- 梯度算出来是 1e-8（fp16 下溢为 0）
- 中间激活达到 1e5（fp16 直接 inf）
- softmax 的 exp 结果都可能超范围

**bf16 的动态范围与 fp32 完全一致**，因此几乎不会溢出，
代价是尾数只有 7 位（约 2 位十进制精度）——但对神经网络训练已经足够。

**历史背景**：Google TPU 原生支持 bf16（2018 起），
NVIDIA 从 A100（2020）开始支持。这也是 bf16 在 LLM 时代成为默认的原因。

## 混合精度的标准配方

不是"全部用 bf16"，而是**混合**：

| 部分 | 精度 | 理由 |
| --- | --- | --- |
| 前向/反向的矩阵乘 | **bf16** | 占绝大部分算力，用低精度加速 |
| 权重的主副本（master weights） | **fp32** | 参数更新需要精度，避免累积误差 |
| 梯度累加 | **fp32** | 小数相加在 bf16 下会丢失 |
| 优化器状态（m, v） | **fp32** | 同上 |
| LayerNorm / softmax / loss | **fp32** | 数值敏感操作 |
| 归约（all-reduce） | **fp32** | 跨卡求和的精度 |

**核心思想**：**计算用低精度（快），存储和累加用高精度（准）**。

## 为什么需要模糊去重

精确哈希只能抓**完全相同**的文档。但互联网上大量是"改了几个字"的转载：

    原文：今天天气很好，我们一起去公园散步吧。
    转载：今天天气不错，我们一起去公园走走吧。

哈希完全不同，但显然是重复内容。

**目标**：用一个短签名（signature），使得
**相似文档的签名大概率相同，不相似的大概率不同**。

## Jaccard 相似度

定义两个集合（这里是文档的 shingle 集合）的相似度：

    J(A, B) = |A ∩ B| / |A ∪ B|

**Shingle**：把文档切成 k 个连续词的片段（k 通常 5 或 9）。
例如 "a b c d e f" 在 k=3 时，shingle 是 {abc, bcd, cde, def}。

两篇"改了几个字"的文档，其 shingle 集合的 Jaccard 相似度通常 > 0.8。

## MinHash 的核心思想

**问题**：直接算 Jaccard 需要比较所有 shingle，太慢（O(文档长度)）。

**MinHash 的巧妙之处**：用**随机哈希**近似 Jaccard。

    对集合 S 的每个元素用哈希函数 h 求值，取最小值：
    minhash(S) = min{ h(x) : x ∈ S }

**关键定理**：两个集合的 minhash 值相同的概率，等于它们的 Jaccard 相似度：

    P(minhash(A) == minhash(B)) = J(A, B)

**所以**：用 k 个不同的哈希函数，得到 k 维签名；
比较两个签名**对应位置相同的比例**，就是 Jaccard 的估计值。

    # 签名 A: [3, 7, 1, 9, 2]
    # 签名 B: [3, 7, 5, 9, 8]
    # 相同位置: 3/5 → 估计相似度 0.6

**为什么**：如果 A、B 的并集里最小哈希值落在交集元素上，
两个集合的 minhash 就相同。而这个概率正是 J(A,B)。

## LSH：把 O(n²) 比较降到近似 O(n)

去重时文档有上亿篇，两两比较不可能。

**LSH（Locality-Sensitive Hashing）**：
把 k 维签名分成 b 个 band，每个 band 有 r 个哈希值（k = b × r）。

    band1: [3, 7]  -> 哈希成一个桶 key
    band2: [1, 9]  -> 另一个桶 key
    ...

**规则**：只要**任意一个 band 完全相同**，两篇文档就被判为候选重复对。

**调节 b 和 r 的意义**：
- b 越大 → 越容易撞上 → 召回率高但误判多；
- r 越大 → 每个 band 越难完全相同 → 精确率高但召不回。

实测常用：**k=128~256，b=32~64**。

**效果**：从 O(n²) 降到近似 O(n)，上亿文档可在数小时内完成去重。

## 什么是 Scaling Law

**核心问题**：给定固定的算力预算，应该训多大的模型、用多少数据？

**Scaling Law 的答案**：损失 L 与参数量 N、数据量 D、算力 C 之间存在**幂律关系**：

    L(N) ∝ N^(-α)      α ≈ 0.076
    L(D) ∝ D^(-β)      β ≈ 0.095

**幂律的含义**：模型规模翻 10 倍，loss 下降一个固定比例（而不是线性的收益）。
这意味着**收益递减但从不停止**——这就是"更大模型更好"的理论基础。

## Kaplan et al. (2020) 的结论

OpenAI 的研究（GPT-3 同期）给出的建议：

> **在固定算力下，应该优先增大模型参数，数据量只需温和增长。**

具体配比：N ∝ C^0.73，D ∝ C^0.27。

**实践后果**：GPT-3（175B）只训练了 300B token——
**每个参数约 1.7 个 token**。这在现在看来是"训练不足"的。

## Chinchilla (2022) 的修正

DeepMind 重新做了实验，发现 Kaplan 的结论**有系统性偏差**（学习率调度与训练 token 数不匹配）。

**修正后的结论**：

> **在固定算力下，参数量与数据量应该同比例增长。**
>
> **最优配比：D ≈ 20 × N**（每个参数训 20 个 token）

**对比**：

| 模型 | 参数量 | 训练 token | 比例 | 评价 |
| --- | --- | --- | --- | --- |
| GPT-3 | 175B | 300B | 1.7:1 | **严重不足** |
| Chinchilla | 70B | 1.4T | 20:1 | 最优 |
| LLaMA-1 7B | 7B | 1T | 143:1 | **远超** |
| LLaMA-3 8B | 8B | 15T | 1875:1 | **极端过训** |

**关键洞察**：Chinchilla 70B 的效果**超过了 GPT-3 175B**，
而推理成本只有 1/2.5——因为它的参数更少但训得更充分。

## 为什么 LLaMA 系列"过度训练"

Chinchilla 的最优配比是**在训练算力固定**的前提下最优。

但实际部署时，**推理成本远大于训练成本**：
一个模型上线后要服务数百万次请求，推理成本可能是训练的 100 倍。

**所以工业界的选择**：故意"过训"小模型——
多花训练算力，换取一个**参数更少、推理更快**的模型。

    Chinchilla 最优：训练成本 + 推理成本 的总和最小
    LLaMA 的选择：牺牲训练效率，换取推理效率

**这就是"Chinchilla-optimal"与"inference-optimal"的区别。**
