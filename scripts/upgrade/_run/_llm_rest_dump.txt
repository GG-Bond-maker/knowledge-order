## 为什么需要 RAG

大模型的知识**固定于训练时点**，且容易"一本正经地胡说"（幻觉）。RAG（Retrieval-Augmented Generation）通过**检索外部知识库**，把相关内容放入上下文再生成。

**优点**：

1. 知识可实时更新（改文档即可，无需重训）；
2. 可引用来源，便于核查；
3. 降低幻觉率；
4. 可处理私有数据。

## RAG 的五个阶段

```
① 切分（Chunking） → ② 向量化（Embedding） → ③ 存储（Vector DB）
                                    ↓
⑥ 生成（Generation） ← ⑤ 重排（Rerank） ← ④ 检索（Retrieval）
```

## ① 文档切分（Chunking）：最容易被低估的一步

**为什么要切分**：上下文窗口有限，且检索粒度太粗会引入无关内容。

**切分策略对比**：

| 策略 | 说明 | 优缺点 |
| --- | --- | --- |
| 固定长度 | 每 N 个字符/token 一段 | 简单，但会切断语义 |
| 按段落/句子 | 按自然边界切 | 语义完整，长度不均 |
| 递归切分 | 优先按段落，过长再按句子 | **最常用** |
| 语义切分 | 用 embedding 判断语义断点 | 效果好但成本高 |
| 父子切分 | 小块用于检索，大块用于生成 | 兼顾精度与上下文 |

**关键参数**：

- **chunk size**：常见 200~1000 token。太小则语义不完整，太大则噪声多；
- **chunk overlap**：相邻块重叠 10%~20%，避免边界信息丢失。

```python
def chunk_by_chars(text, size=500, overlap=50):
    chunks = []
    start = 0
    while start < len(text):
        end = start + size
        chunks.append(text[start:end])
        start = end - overlap
    return chunks
```

## 为什么 RAG 必须评估

RAG 系统"看起来能用"不代表可靠。没有评估，就无法判断改动是提升还是倒退。

## RAG 评估的三个层次

**1. 检索质量（Retrieval）**

| 指标 | 含义 |
| --- | --- |
| Recall@K | 前 K 个结果中是否包含正确答案所在文档 |
| Precision@K | 前 K 个结果中相关文档的比例 |
| MRR | 第一个正确结果的排名倒数均值 |
| NDCG | 考虑位置的排序质量 |

**2. 生成质量（Generation）**

| 指标 | 含义 | 评估方式 |
| --- | --- | --- |
| **忠实度（Faithfulness）** | 回答是否有资料支撑、无编造 | 用 LLM 判断每个论断能否在资料中找到依据 |
| **答案相关性（Answer Relevancy）** | 回答是否切题 | LLM 判断 |
| **上下文召回（Context Recall）** | 资料是否覆盖了回答所需信息 | 与标准答案对比 |
| **上下文精确（Context Precision）** | 检索到的资料是否都有用 | LLM 判断 |

这些构成了 RAGAS 等评估框架的核心指标体系。

**3. 端到端**

- 人工打分（准确、有帮助、无幻觉）；
- A/B 测试（用户满意度、任务完成率）。

## 构建评估集的实用方法

1. **从真实问题出发**：收集 50~200 个真实用户问题；
2. **标注标准答案与依据文档**；
3. **覆盖类型**：简单事实、需要多文档综合、无法回答（应说不知道）、易混淆概念；
4. **版本化**：每次改 prompt / 切分策略 / 模型，都跑一遍评估集。

**"无法回答"类样本尤其重要**——它能暴露模型是否在编造。

## 常见失败模式与对策

| 现象 | 根因 | 对策 |
| --- | --- | --- |
| 答非所问 | 检索未召回相关内容 | 改切分、加混合检索、加同义词、调 embedding |
| 编造细节 | 提示未约束"仅依据资料" | 加约束 + 要求引用 + 降低温度 |
| 综合多个文档出错 | 上下文过长、信息冲突 | 重排取 Top-K、明确冲突处理规则 |
| 该说不知道时乱答 | 缺少拒答训练 | 提示中给出拒答示例（few-shot）|
| 回答太长太啰嗦 | 未限制格式 | 明确长度与结构要求 |

## 一个残酷的事实

**如果切分把答案切断了，后面再强的 embedding 和模型都救不回来。**

检索的基本单位是 chunk（块）。一个 chunk 是"检索时能命中的最小语义单元"：

- **块太大**：包含大量无关内容，向量被"稀释"，检索精度下降；同时挤占上下文预算。
- **块太小**：语义不完整，答案被拆散，检索到了也拼不出完整信息。

## 四种主流切分策略

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **固定长度** | 每 N 个字符/token 切一刀 | 实现最简单、块大小均匀 | 会切断句子、表格、代码 |
| **递归切分** | 先按段落切，过长再按句子，再过长才按字符 | 尽量保留自然边界 | 块大小不均 |
| **语义切分** | 用 embedding 计算相邻句相似度，在"语义跳变"处切 | 语义最完整 | 成本高、需额外模型 |
| **父子切分** | 小块用于检索，大块（父块）用于喂给模型 | 兼顾检索精度与上下文完整 | 需要两层存储 |

## 递归切分：最常用的默认方案

LangChain 的 `RecursiveCharacterTextSplitter` 就是这个思路。分隔符优先级：

    ["\n\n", "\n", "。", "！", "？", "；", "，", "", "..."]

先用最高优先级（段落）切，若某段仍超过 chunk_size，再用下一级（行、句子）切，
直到满足大小限制。这样能**尽可能保留语义边界**。

```python
def recursive_split(text, size, separators):
    for sep in separators:
        if sep and sep in text:
            parts = text.split(sep)
            # 合并小片段直到接近 size
            ...
    return [text]  # 兜底：按字符硬切
```

## 关键参数

**chunk_size**：常见 200~1000 token。

| 场景 | 建议 |
| --- | --- |
| FAQ、短文档问答 | 200~400 |
| 通用企业知识库 | 500~800 |
| 需要大段上下文的法规/合同 | 800~1500 |
| 代码仓库检索 | 按函数/类切（语法感知） |

**chunk_overlap**：相邻块重叠 10%~20%，防止边界信息丢失。
比如 chunk_size=500、overlap=50。

**注意 token vs 字符**：中文约 1.5~2 字符

## 向量检索（Dense Retrieval）

把 query 和 doc 都编码成向量，用余弦相似度找最近的。

**优势**：
- 理解**语义**——"怎么退款"能匹配到"退换货政策"；
- 跨语言、同义词、改写友好。

**劣势**：
- **精确匹配弱**——产品型号 "XR-2000"、"ERR_5001" 这类字符串，
  向量模型可能编码得很模糊；
- 需要 embedding 模型与索引，成本较高；
- 对**罕见词、专有名词**效果差（训练数据里没见过）。

## 关键词检索（Sparse / BM25）

BM25 是 TF-IDF 的改进版，按词频与逆文档频率打分：

    score(q, d) = Σ IDF(qᵢ) · (tf · (k₁+1)) / (tf + k₁·(1-b+b·|d|/avgdl))

**优势**：
- **精确匹配极强**——型号、编号、人名、代码标识符；
- 不需要训练，可解释（能看出是哪个词命中）；
- 对罕见词天然友好（IDF 高）。

**劣势**：
- 不懂语义，"怎么退款" 匹配不到 "退换货政策"；
- 依赖分词质量（中文尤其明显）。

## 混合检索（Hybrid）

同时跑两路，融合结果。这是**工业界的主流做法**。

**为什么有效**：两路召回的错误不相关——向量漏掉的精确匹配、BM25 漏掉的语义匹配，
合起来召回率显著提升。

## 分数融合的难题

向量分数（0~1 的余弦）和 BM25 分数（0~几十的无界值）**量纲完全不同**，
不能直接相加。两种解法：

**1. 归一化后加权**

    score = α · norm(vector_score) + (1-α) · norm(bm25_score)

需要选 α，且归一化方式（min-max vs z-score）影响结果。

**2. RRF（Reciprocal Rank Fusion）—— 更鲁棒**

只用**排名**，不用分数：

    RRF(d) = Σᵢ 1 / (k + rankᵢ(d))

k 通常取 60。**优点**：完全绕过量纲问题，无需调参，实践中效果好。

```python
def rrf(rankings, k=60):
    scores = {}
    for rl in rankings:
        for rank, doc in enumerate(rl, 1):
            scores[doc] = scores.get(doc, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

## 为什么必须评估

没有评估集的 RAG 优化就是"猜"：改一个参数，感觉好像变好了，但可能只是变了个错误方式。

## 两层评估

**检索层：召回得准不准**

| 指标 | 定义 | 关注点 |
| --- | --- | --- |
| Recall@K | 前 K 个结果中，包含的"相关文档"占全部相关文档的比例 | **有没有漏** |
| Precision@K | 前 K 个结果中，相关文档的占比 | **有没有噪声** |
| MRR | 第一个相关结果排名的倒数（1/rank） | **排得靠不靠前** |
| NDCG@K | 考虑位置权重的排序质量 | 综合排序质量 |
| Hit Rate@K | 前 K 中至少有一个相关结果的比例 | 简单直观 |

**RAG 场景最关键的是 Recall@K**——只要相关文档被召回到候选里，重排和生成都还有机会；
若召回阶段就漏了，后面再强也没用。

**生成层：答得对不对**

| 指标 | 定义 | 怎么算 |
| --- | --- | --- |
| **忠实度 Faithfulness** | 回答中的每个论断能否在检索到的上下文中找到依据 | LLM 逐句判定 |
| **答案相关性 Answer Relevancy** | 回答是否切题 | LLM 判定 / embedding 相似度 |
| **上下文精确度 Context Precision** | 检索到的上下文里有用信息的比例 | LLM 判定每条是否相关 |
| **上下文召回率 Context Recall** | 上下文是否覆盖了回答所需的全部信息 | 与标准答案对比 |

这四个构成了 **RAGAS** 框架的核心指标。

## 忠实度：RAG 最重要的指标

忠实度衡量"有没有编造"：

    忠实度 = 能被上下文支撑的论断数 / 回答中的总论断数

计算方式（LLM-as-Judge）：

1. 把回答拆成若干独立论断（claim）；
2. 对每个论断，判断能否从检索到的 context 中推出；
3. 计算比例。

**为什么它最重要**：RAG 的核心承诺就是"基于资料回答"。如果忠实度低，
说明模型在编造，整个 RAG 就失去了意义。

## Naive RAG 的三个根本问题

前面讲的 RAG 是**固定流程**：总是检索 → 总是取 top-k → 总是塞进上下文。

**问题 1：不需要检索时也检索**
问「1+1等于几」也去检索，浪费成本还可能引入噪声。

**问题 2：检索到无关内容也照用**
top-k 里可能有一半是不相关的，模型会被误导。

**问题 3：检索一次就结束**
复杂问题可能需要**多轮检索**、逐步深入。

**高级 RAG 的共同思路**：把"检索"从固定步骤变成**可决策、可迭代**的动作。

## Self-RAG：让模型自己决定要不要检索

**论文**：Self-Reflective Retrieval-Augmented Generation (arXiv 2310.11511)

**核心创新**：训练模型生成**反思标记（reflection tokens）**，
用这些特殊 token 显式表达"要不要检索""这段内容有用吗""我的回答有支持吗"。

**四类反思标记**：

| 标记类型 | 取值 | 含义 |
| --- | --- | --- |
| **Retrieve** | yes / no / continue | 是否需要检索 |
| **IsRel** | relevant / irrelevant | 检索到的段落是否相关 |
| **IsSup** | fully / partially / no | 回答是否有段落支持 |
| **IsUse** | 1~5 | 回答整体有用性 |

**推理流程**：

    问题 → 模型判断 [Retrieve=yes?]
              ├─ no  → 直接用参数知识回答
              └─ yes → 检索 k 个段落
                        ↓
                 对每段判断 [IsRel]
                        ↓
                  生成回答 + [IsSup] 标记
                        ↓
                  按 [IsUse] 排序候选答案，选最佳

**关键点**：这些标记是**训练出来的**，不是提示词。
需要构造带标记的训练数据，用标准语言建模目标训练。

**收益（论文实测）**：
- 7B/13B 的 Self-RAG 在开放域 QA、推理、事实验证上**超过 ChatGPT**；
- 长文生成的**事实性与引用准确性**显著提升。

**代价**：
- 需要专门训练（非即插即用）；
- 推理时多次调用，延迟增加。

## 传统 RAG 处理不了的问题

**论文**：From Local to Global: A Graph RAG Approach to
Query-Focused Summarization (Microsoft, arXiv 2404.16130)

**核心洞察**：RAG 在**全局性问题**上会失败。

    局部问题（RAG 擅长）：
      "张三的职位是什么？"
      → 能定位到包含答案的少数段落

    全局问题（RAG 失效）：
      "这份数据集的主要主题是什么？"
      "这些文档里有哪些反复出现的风险因素？"
      "整个语料对企业战略的描述有什么矛盾？"
      → 答案不在任何单个段落里，需要**跨全库综合**

**根本原因**：这类问题本质是 **query-focused summarization（QFS）**，
不是检索问题。top-k 检索只能看到局部，看不到全局。

**难点**：直接把全部语料塞进上下文？100 万 token 的语料放不进去，
而且中间信息会被忽略（lost in the middle）。

## GraphRAG 的两阶段方案

**阶段 1：用 LLM 构建图谱索引**

    源文档
      ↓ ① 分块（chunk）
      ↓ ② 每个 chunk 让 LLM 抽取实体与关系
    实体知识图谱（节点=实体，边=关系）
      ↓ ③ 社区检测（Leiden 算法，把紧密相连的实体分组）
    层级化的社区结构
      ↓ ④ 为每个社区预生成摘要（LLM）
    社区摘要索引

**阶段 2：查询时用摘要生成部分回答**

    问题
      ↓ 对每个社区摘要生成一个"部分回答"
      ↓ 所有部分回答再汇总（map-reduce）
    最终回答

**这就是 map-reduce 的思路**：先局部作答，再全局汇总。

## 社区检测与层级

**社区（community）**：图中联系紧密的实体群组。

**Leiden 算法**：一种层级化社区检测，产出多层级结构：

    Level 0: 整个语料（1 个社区）
    Level 1: 几个大主题（如 5-10 个社区）
    Level 2: 每个大主题下的细分主题（如 50 个社区）
    Level 3: 更细的实体群组（如 500 个社区）

**为什么需要层级**：
- 问"主要主题" → 用 Level 1 的摘要（粗粒度）；
- 问"某个细分领域的风险" → 用 Level 2/3（细粒度）。

**摘要生成**：每个社区用 LLM 生成一段摘要，描述该社区实体的共性主题。
这是**离线预计算**的，查询时直接复用。

## 预训练模型的"能用"与"好用"

预训练模型学会的是"预测下一个 token"：它知道大量事实、语法与推理模式，但并不天然知道"应该怎么回答用户"。直接让基座模型接任务，常见表现是：

- 把问题续写成新的问题（"北京是中国的什么？首都还有广州、上海……"）；
- 输出格式不可控；
- 对有害请求不拒绝；
- 不知道"回答不清楚时承认不知道"。

后训练（Post-training）就是把"能力"转化为"可用行为"的过程，通常分三步：

1. **监督微调 SFT**：用"指令-回答"对教模型遵循格式与指令；
2. **偏好对齐 RLHF / DPO**：用人类偏好数据调整风格、有用性与安全性；
3. **推理增强与蒸馏**：用更强的模型或可验证奖励提升特定能力（数学、代码）。

## 什么时候该微调，什么时候不该

| 需求 | 推荐做法 |
| --- | --- |
| 改变输出格式/风格 | 提示工程 + few-shot，通常够用 |
| 注入大量私有知识 | RAG，而不是微调（知识更新快、可追溯） |
| 固定领域的细分任务（分类、抽取、改写） | 微调小模型，效果好且便宜 |
| 需要稳定遵循复杂规则（多约束、强格式） | SFT 微调 |
| 需要降低延迟与成本 | 蒸馏到小模型 + 微调 |
| 需要新的推理能力 | 继续预训练 + 大规模后训练（成本极高） |

**关键判断**：微调擅长"改变行为与格式"，不擅长"记住新知识"。知识型需求优先考虑 RAG；两者可以结合——先用 RAG 提供事实，再用微调固定回答的结构与口径。

## 数据、算法、工程三要素

一次成功的微调取决于：

1. **数据**（约 60% 权重）：数量够不够、质量高不高、覆盖是否全面、有无泄漏；
2. **算法**（约 20%）：全参还是 PEFT、学习率、批次、序列长度、loss 掩码；
3. **工程**（约 20%）：显存、并行、评测、部署与服务化。

现实中最常见的失败原因是数据问题，而不是算法选择。

## 一次典型的微调项目流程

1. **定义任务与评测**：先写 100 条测试集，明确"成功的标准"；
2. **构造数据**：人工标注 + 模型生成后人工审核 + 从生产日志挖掘；
3. **基线**：先不微调，用提示工程 + few-shot 跑一遍评测，得到对照基线；
4. **训练**：从小规模 LoRA 开始，只跑几百步看 loss 与生成样例；
5. **评测**：客观指标 + LLM 裁判 + 人工抽检，三者交叉验证；
6. **部署**：量化、合并适配器、压测、灰度；
7. **迭代**：把线上 badcase 转成新的训练样本。

## 全参微调（Full Fine-tuning）

更新模型全部参数。优点是表达能力强；代价是显存与灾难性遗忘：

- **参数显存**：N 个参数 × 2 字节（BF16）；
- **梯度**：再 × 2 字节；
- **优化器状态**（Adam 的动量与方差）：再 × 8 字节（FP32）。

合计约 **16 N 字节**，7B 模型约 112 GB，远超单卡容量。因此全参微调必须配合 ZeRO（把参数、梯度、优化器状态分片到多卡）、FSDP 或张量并行。

## LoRA：低秩增量

Hu et al.（2021）提出：冻结原权重 W（形状 d 乘 k），只训练一个低秩分解的增量：

W' = W + (alpha / r) · B · A

其中 A 形状 [r, k]、B 形状 [d, r]，r 远小于 d（常见 8、16、32、64）。A 用高斯初始化、B 初始化为零，保证训练开始时增量恰好为 0，不打乱原有能力。

**参数量对比**：原矩阵 d×k，LoRA 为 r×(d+k)。以 d=k=4096、r=16 为例：原 16.7M，LoRA 仅 131K，约为 0.8%。

LoRA 的优势：

1. **显存大降**：只保存适配器的梯度与优化器状态；
2. **可插拔**：一个基座配多个适配器（客服、代码、法务），按请求切换；
3. **易合并**：推理时可把 B·A 加回 W'，零额外延迟；
4. **减轻遗忘**：原权重不动，行为漂移更小。

## 关键超参数

| 参数 | 含义 | 经验值 |
| --- | --- | --- |
| r | 秩，决定容量 | 8~64（简单任务 8，复杂任务 32~64） |
| alpha | 缩放因子 | 常取 2r 或 r |
| target_modules | 应用到哪些层 | 至少 q_proj 与 v_proj，效果更好时加上 k、o 与 MLP |
| dropout | 防过拟合 | 0~0.1 |
| learning_rate | 学习率 | 1e-4 ~ 2e-4（远高于全参微调的 1e-5） |

## QLoRA：4bit 基座 + LoRA

Dettmers et al.（2023）的 QLoRA 用三项技术把 65B 模型塞进 48GB：

1. **4-bit NormalFloat（NF4）**：按正态分位数设计量化区间，适配预训练权重的分布；
2. **双重量化**：对量化常数本身再量化，进一步省显存；
3. **分页优化器**：显存峰值时把优化器状态换出到 CPU，避免 OOM。

效果：4bit 基座 + BF16 LoRA 训练，在多数评测上接近 16bit 全参微调。

## 一条高质量的 SFT 样本长什么样

典型结构（与 chat template 对应）：

```json
{"messages": [
  {"role": "system", "content": "你是银行的合规助理，只依据提供的政策回答"},
  {"role": "user", "content": "这笔跨行转账需要多久到账？"},
  {"role": "assistant", "content": "依据《跨行清算说明》第 3 条：……"}

```

要点：

1. **只对 assistant 段计算损失**，user 与 system 段 mask 掉。否则模型会学着"自己生成问题"，推理时更容易跑偏；
2. 结尾必须有 eos（结束符），否则模型学不到何时停止；
3. 多轮对话要保留完整历史，并保证角色交替正确。

| 来源 | 优点 | 风险 |
| --- | --- | --- |
| 人工标注 | 质量最高 | 贵、慢 |

## 数据多样性的几个维度

- **任务类型**：问答、改写、抽取、分类、多步推理、拒答；
- **难度**：简单格式任务与困难推理任务各占一定比例；
- **长度**：短回答与长回答都要有（否则模型只会输出某一长度）；
- **拒答样本**：必须包含"无法回答时怎么说"的样本，否则模型会幻觉；
- **负例**：告诉模型"什么不该做"，可用偏好对承载。

## 质量控制清单

1. **去重**：精确去重（哈希）与近邻去重（MinHash / embedding 相似度）；
2. **格式校验**：可解析、角色交替正确、无空回复；
3. **事实校验**：涉及事实的回答需人工或检索核对；
4. **泄漏检查**：n-gram 重叠度检查训练集与测试集，避免评测虚高；
5. **长度分布**：统计输入输出长度分布，与线上预期一致；
6. **模板化检测**：同一句式占比过高要补充多样性。

- 任务简单的格式对齐：500~3000 条往往就够；
- 领域知识问答：1 万~10 万条；
- 通用能力提升：需数十万到百万级，且要与预训练分布混合（防止灾难性遗忘）；
- 记住经验：**质量大于数量**，1000 条精标通常胜过 1 万条机器生成未审核数据。

## 自回归生成的性能瓶颈

生成第 t 个 token 时，注意力需要**全部历史 token 的 K、V**。
如果没有缓存，每步都要重算整个前缀，复杂度 O(t²)，整体生成 O(n³)。

**关键洞察**：由于因果掩码，历史 token 的 K、V 在生成过程中**不会改变**。
所以可以缓存下来，每步只算新 token 的 Q、K、V。

<Diagram type="arch" name="kv-cache" />

## KV Cache 的显存公式

    size = 2 × L × S × H_kv × D × bytes

| 符号 | 含义 |
| --- | --- |
| 2 | K 和 V 各一份 |
| L | 层数 |
| S | 序列长度 |
| H_kv | KV 头数 |
| D | 每个头的维度 |
| bytes | 精度字节数（fp16 = 2） |

**以 7B 级模型为例**：L=32, S=4096, H=32, D=128, fp16

    2 × 32 × 4096 × 32 × 128 × 2 = 2.0 GB

**这只是一个请求的 KV Cache**。若并发 32 个用户，就是 64 GB——远超模型权重本身。

## 三个减少 KV Cache 的方向

**1. 减少头数：MQA / GQA**

| 结构 | KV 头数 | KV Cache | 代表模型 |
| --- | --- | --- | --- |
| MHA | = Q 头数（32） | 100% | GPT-3、原始 Transformer |
| GQA | 分组（如 8） | 1/4 | LLaMA 2/3、Qwen |
| MQA | 1 | 1/32 | PaLM、Falcon |

**GQA 是当前主流**：在质量与显存之间取得最佳平衡。
LLaMA 2 70B 用 8 组 GQA，KV Cache 只有 MHA 的 1/8。

**2. 降低精度**

KV Cache 量化到 INT8 / FP8：显存减半，质量损失通常可接受。

**3. 减少长度：滑动窗口 / 稀疏注意力**

只保留最近 W 个 token 的 KV（如 Mistral 的 sliding window attention），
显存变成 O(W) 与序列长度无关。

## 为什么需要批处理

GPU 擅长并行计算。单个请求生成时，大部分算力是闲置的。
把多个请求打包成一个 batch，能显著提升吞吐。

## 静态批处理的问题

**做法**：攒够 N 个请求，一起跑，全部结束后再处理下一批。

**问题**：请求的**生成长度差异极大**。

    [请求 A: 生成 10 个 token]  ■■■
    [请求 B: 生成 200 个 token] ■■■■■■■■■■■■■■■■■■■■
    [请求 C: 生成 50 个 token]  ■■■■■

    A 完成后，那部分算力就**闲置**了，必须等 B 跑完才能开始下一批。

**结果**：GPU 利用率低，平均延迟被最长的请求拖累。

## Continuous Batching（连续批处理）

**核心思想**：以 **token 为粒度**调度，而不是以请求为粒度。

- 每一步解码时，检查是否有请求已完成 → **立即移出 batch**；
- 检查是否有新请求到达 → **立即加入 batch**；
- batch 的大小每一步都可能变化。

    step 1: [A, B, C]
    step 2: [A, B, C]
    step 3: [A, B, C, D]   ← D 到达，加入
    step 4: [B, C, D, E]   ← A 完成，移出；E 加入
    ...

**效果**：GPU 几乎不闲置，吞吐可提升 **5~20 倍**，而单个请求的延迟几乎不变。

**代价**：实现复杂（动态 batch、KV Cache 的动态管理），
这也是 vLLM / TensorRT-LLM 这类引擎的核心价值。

## 两个关键延迟指标

| 指标 | 含义 | 影响 |
| --- | --- | --- |
| **TTFT**（Time To First Token） | 从请求到第一个 token 输出的时间 | 用户"等待感" |
| **TPOT**（Time Per Output Token） | 后续每生成一个 token 的平均耗时 | 阅读速度感知 |

**总延迟** ≈ TTFT + TPOT × 输出 token 数

**优化取舍**：
- 增大 batch → 吞吐上升，但 TTFT 与 TPOT 都会变差；
- 流式输出降低"体感 TTFT"（用户先看到字）；
- 前缀缓存能显著降低 TTFT（相同系统提示无需重算）。

## 成本从哪里来

调用 API 时按 token 计费，**输入与输出价格不同**（输出通常贵 3~5 倍）：

| 模型档位 | 输入（$/M tokens） | 输出（$/M tokens） |
| --- | --- | --- |
| 小模型 | 0.1~0.5 | 0.4~1.5 |
| 中模型 | 1~3 | 4~15 |
| 大模型 | 5~15 | 15~75 |

**成本 = 输入 token × 输入单价 + 输出 token × 输出单价**

自建推理则按 GPU 小时计费，成本取决于吞吐与利用率。

## 输入侧优化

**1. 精简系统提示**

系统提示在每个请求里重复。一个 1000 token 的系统提示，
100 万次请求 = 10 亿 token —— 这笔钱完全可以省。
能 200 字说清的就别写 1000 字。

**2. Prompt Caching（前缀缓存）**

把固定的系统提示 / 长文档前缀缓存起来，后续请求命中缓存时**按极低价格计费**
（很多厂商对缓存命中的输入收 10% 甚至更低）。

**适用场景**：系统提示长、多轮对话、RAG 中相同的文档被反复查询。

**要求**：前缀必须**完全一致**（一个字都不能变），所以要把可变内容放在后面。

**3. 裁剪上下文**

- RAG 只放 Top-3 而非 Top-10；
- 工具返回结果先摘要再放入；
- 历史对话做滑动窗口或摘要压缩。

## 输出侧优化

- 设置 `max_tokens` 上限；
- 提示中要求简洁（"不超过 100 字"、"只输出 JSON"）；
- 用结构化输出减少冗余文字。

## 模型路由：最大的降本杠杆

**不是所有请求都需要最强模型**：

    def route(query, complexity):
        if is_simple(query):        return small_model    # 分类、抽取、短问答
        if needs_reasoning(query):  return large_model    # 数学、多步推理、代码
        return medium_model

**收益**：成本可降 50%~80%，大多数简单请求质量不受影响。
**风险**：路由判断错误会让简单请求变差或复杂请求变弱。

**实现方式**：
- **规则路由**：按长度、关键词、是否含代码块判断；
- **小模型分类**：用一个小模型判断复杂度（额外一次调用，但很便宜）；
- **级联（Cascade）**：先小模型回答，置信度低时再升级到大模型。

## 为什么 SFT 之后还要对齐

SFT 教会了「怎么回答」，但没教「回答得多好」。具体问题：

- 同一问题可能有多个正确答案，SFT 只学了**一个**；
- SFT 无法表达「这个回答比那个更好」这种**相对偏好**；
- 模型可能输出有害、不诚实、啰嗦的内容。

**对齐（Alignment）的目标**：让模型输出符合人类偏好——
有用（helpful）、诚实（honest）、无害（harmless），即 **3H**。

## RLHF 三阶段（InstructGPT 流程）

**阶段 1：SFT**

用指令数据微调，得到一个「会回答」的模型。

**阶段 2：训练奖励模型（Reward Model）**

收集**人类偏好对比数据**：同一个问题给两个回答，标注哪个更好。

    问题: 如何学习数据分析？
    回答A: 先学 Python，再做项目...        <- 人类选 A
    回答B: 数据分析很重要，要多练习...      <- 被拒绝

**损失函数**（Bradley-Terry 模型）：

    L = -log sigmoid( r(chosen) - r(rejected) )

即：让好回答的分数比坏回答**至少高出一个 margin**。

**阶段 3：用 PPO 强化学习优化策略**

用奖励模型给模型输出打分，PPO 更新策略：

    reward = RM(prompt, response)
    # 但要加 KL 惩罚，防止偏离 SFT 模型太远
    total = reward - beta * KL(new_policy || sft_policy)

**KL 惩罚的作用（关键）**：
- 奖励模型只是人类偏好的**近似**，模型会找到「欺骗」它的方式（reward hacking）；
- KL 约束让新模型不要偏离 SFT 模型太远，保持语言能力；
- beta 通常取 0.01~0.1。

## PPO 的复杂性

PPO 需要**四个模型同时驻留显存**：

| 模型 | 作用 | 参数量 |
| --- | --- | --- |
| Actor（策略） | 被训练的模型 | 1 份 |
| Critic（价值） | 估计 baseline | 1 份 |
| Reward Model | 打分 | 1 份 |
| Reference Model | 算 KL | 1 份 |

**总计约 4 倍模型显存**。70B 模型做 RLHF 需要 4×140GB = 560GB，
还要加上优化器状态与激活——**极其昂贵**。

这就是 DPO 出现的动机。

## 从人类偏好到严谨推理：后训练的范式跃迁

在前面两章中，我们讨论的 RLHF 与 DPO 的核心目标是**符合人类偏好与安全对齐**。
然而，2024-2025 年以 OpenAI o1 和 DeepSeek-R1 为代表的“推理模型（Reasoning Models）”，开辟了全新的强化学习维度：**让大语言模型掌握严密的逻辑推导、数学证明与代码编写能力**。

在这些任务中，我们不需要模糊的人类偏好打分，因为**数学与代码的答案是非分明、客观可判定的**。
这催生了 **RLVR（Reinforcement Learning with Verifiable Rewards，可验证奖励的强化学习）**。

## RLVR 的核心机制与奖励设计

与传统依赖易受攻击（Reward Hacking）的神经奖励模型（Reward Model）不同，RLVR 完全依赖**确定性规则引擎**作为裁判：

| 任务类型 | 验证判定方式 | 奖励机制 ($r$) |
| --- | --- | --- |
| **数学推导** | 正则匹配提取 LaTeX \boxed{} 答案与标准答案比对 | 严格匹配=1.0，错误=0.0 |
| **代码算法** | 在沙箱环境中针对隐藏单元测试用例执行 | 全部通过=1.0，失败=0.0 (或按通过率梯级打分) |
| **格式规范** | 正则检验 <think>...</think><answer>...</answer> 标签闭合性 | 结构合规=0.2，缺失标签=0.0 |
| **语言一致性** | 检测思考链中的语言分布（防止中英文无序混杂） | 语言纯正=1.0，严重混杂扣分 |

### RLVR 的核心优势与局限
- **优势**：
  1. **绝对防作弊**：客观单元测试无法通过谄媚或冗长文字被糊弄，不存在 Reward Hacking 空间；
  2. **数据无限自举**：数学与代码题目可以通过符号系统自动批量生成，无需昂贵的人工标注。
- **局限**：
  仅适用于**结果具有确定判定准则**的任务，无法直接用于开放式文学写作或主观哲学探讨。

4. **价值网络（Critic Network $V_\phi$）**：估计基线（Baseline）以降低策略梯度的方差。

## MoE 训练为什么不稳定

稀疏路由引入了**动态的、不可微的**选择：
- 梯度只流向被选中的专家（未选中的专家没有梯度）；
- 路由决策在离散空间中跳变；
- 专家负载波动导致数值尺度变化。

Switch Transformer 论文系统总结了让 MoE 稳定训练的技巧。

## 1. 选择性精度：用 bfloat16 而非 float16

**问题**：fp16 的动态范围只有约 ±65504，MoE 中路由与专家输出容易出现极大/极小值，导致溢出。

**方案**：用 **bfloat16**——指数位与 fp32 相同（8 位），
动态范围与 fp32 一致，只是尾数精度低（7 位）。

**关键实践**：
- router 的 logits 与 softmax 用 float32（精度敏感）；
- 专家内部的矩阵乘用 bf16（吞吐优先）。

## 2. 更小的初始化

**问题**：MoE 专家数量多，若用常规初始化，输出尺度容易失控。

**方案**：把专家权重与嵌入层的初始化尺度**缩小 10 倍**（如 std 从 0.02 降到 0.002）。

Switch 论文明确指出这一步显著改善稳定性。

## 3. 增大 dropout（仅在微调阶段）

论文发现在**微调**阶段，MoE 需要比稠密模型更大的 dropout
（如 0.1 而非 0.01），否则容易过拟合。

## 4. 专家并行与 all-to-all 通信

大规模训练时，专家分布在不同设备上：

    1. 每个设备算本地 token 的门控分数
    2. all-to-all：把 token 发送到对应专家所在设备
    3. 各设备本地计算自己的专家
    4. all-to-all：把结果发回原设备

**通信量**：每层两次 all-to-all，数据量 ∝ token 数 × d_model。
这是 MoE 在大规模下的主要瓶颈，也是为什么 MoE 通常需要高速互联（NVLink/InfiniBand）。

**1. 相同算力下 MoE 更优**

- 预训练速度提升约 **7 倍**；
- 在多个下游任务（SuperGLUE 等）上效果更好。

**2. 相同的计算量，MoE 效果超过更大的稠密模型**

Switch-XXL（395B 参数）在多任务上显著优于 T5-XXL（11B 稠密），

## 核心思路：化整为零，细粒度切分

为了解决粗粒度专家的知识混杂与组合不足，DeepSeek 团队提出了 **细粒度专家切分（Fine-Grained Expert Segmentation）** 策略：

> **思想**：保持激活计算量（FLOPs）严格不变的前提下，把原本庞大的大专家，**切碎成更多更小的子专家**，并成倍增加激活专家的数量！

## 数学切分方案

设原本的粗粒度 MoE 拥有 $N$ 个专家，每个专家 FFN 的中间隐层维度为 $d_{\text{ff}}$，每个 Token 激活 $K$ 个专家。

DeepSeek-MoE 将每个专家沿中间维度切分成 $m$ 个更小的细粒度专家：
- **总专家数**：$N_{\text{fine}} = m \times N$
- **单专家隐层维度**：$d_{\text{fine}} = \frac{d_{\text{ff}}}{m}$
- **激活专家数**：$K_{\text{fine}} = m \times K$

### 计算量（FLOPs）守恒证明
每个 Token 经过激活专家的计算开销为：
$$\text{FLOPs} \propto K_{\text{fine}} \times d_{\text{fine}} = (m \cdot K) \times \left( \frac{d_{\text{ff}}}{m} \right) = K \cdot d_{\text{ff}}$$
计算量**丝毫不增**，显存访存带宽需求完全一致！

## 分布式 MoE 的天堑：专家并行（EP）与通信

在千亿参数规模下（例如 DeepSeek-V3 拥有 256 个路由专家，总参数 671B），单一 GPU 显卡无法容纳全部专家，必须采用 **专家并行（Expert Parallelism, EP）**：
- 将 256 个专家均匀分散在由许多台服务器构成的 GPU 集群中（例如 32 台服务器，每台 8 张 H800，共 256 卡，每卡存放 1 个专家）。

### 致命的跨机 All-to-All 通信
每个 Token 被不同 GPU 上的注意力层计算完成后，需要根据门控决策，**通过网络发送给对应的专家所在的 GPU**。
在专家计算完成后，还要通过网络将结果发回原始 GPU。
这构成了极度密集的 **All-to-All 全交换跨机网络通信**！

跨机网络带宽（以太网 RoCE 或 InfiniBand 400Gbps）远小于机内 NVLink（900GB/s），跨机网络拥堵会直接导致整个 GPU 集群长时间陷入通信等待停顿！

## DeepSeek-V3 的设备受限路由（Device-Limited Routing）

为了斩断跨机通信的咽喉，DeepSeek-V3 提出了 **设备受限路由机制**：

> **规则**：对于任意一个 Token，尽管它需要激活 8 个路由专家，但门控路由施加硬性约束：**选出的这 8 个专家，所驻留的物理机节点数量最多不能超过 $M$ 个（例如 $M \le 4$）**！

```
             Token 待选 8 个专家
               /              \
    [传统无约束路由]          [设备受限路由]
    专家分散在 8 个不同机柜   专家被约束在最多 4 台机器内
    产生 8 条跨机传输流       产生跨机通信流减半，机内 NVLink 分担
    网络拥塞，通信成为瓶颈   极致压减跨机吞吐，通信开销大幅降低
```

### 实施策略
1. 首先计算每个专家所在的节点综合打分（Node Affinity）；
2. 选出得分最高的 $M$ 个候选物理机节点；
3. 随后仅在这 $M$ 个物理机所包含的专家子集中挑选出 Top-$K$ 个路由专家。

这种通信拓扑感知路由（Topology-Aware Routing）将集群跨节点网络的并发链接数和传输量削减了 50% 以上，使得千卡集群的专家并行扩展效率维持在 90% 以上！

## 训练爽快，推理头疼：MoE 的部署实战法则

许多团队在第一次落地 MoE 时会陷入误区：“既然 DeepSeek-V3 激活参数只有 37B，那我拿两张 80G A100 是不是就能把它跑起来？”
**答案是绝对不行！**

### 1. 显存占用的残酷现实：总参数决定显存下限
- **训练/推理显存占用**：
  即便每个 Token 只经过 37B 激活参数，**模型全部 671B 参数必须常驻在显存中**！
  - FP16/BF16 权重：$671 \text{B} \times 2 \approx 1342 \text{ GB}$（至少需要 17 张 80G GPU 才能放得下权重！）；
  - FP8 量化权重：$671 \text{B} \times 1 \approx 671 \text{ GB}$（至少需要 9~10 张 80G GPU）；
  - INT4 量化权重：约 $340 \text{ GB}$（至少 5 张 80G GPU）。
- **结论**：**MoE 节省的是计算算力（FLOPs）与生成时间（延迟），而不是显存容量！**

## 推理阶段的专家负载倾斜（Expert Skewing）

在离线批量生成或高并发在线推理时，MoE 面临严重的**长尾倾斜**：
- 某些通用领域的专家（如处理日常对话的专家）命中率极高，承载了大量 Token；
- 某些专业领域的冷门专家处理的 Token 很少。

在张量并行与专家并行服务中，这会导致承载热门专家的 GPU 跑满算力，而其他 GPU 处于闲置等待状态，拖慢整个 Batch 的生成速度。

### 生产级应对方案
1. **动态批处理（Dynamic Batching）与 Token 重组**：
   vLLM 等现代推理引擎通过建立专家维度的 Token Queue，将分配给同一专家的 Token 跨请求打包成致密的 GEMM 计算，提升硬件 MFU；
2. **多副本部署（Replicated Hot Experts）**：
   通过在线统计，将最高频的前 5% 热门专家复制多份并放置在所有 GPU 上（类似于共享专家），分流流量热点；
3. **推测解码（Speculative Decoding）加速**：
   利用小型稠密模型或者共享专家快速生成草稿 Token，再由完整 MoE 进行并行验证，进一步榨干 GPU 内存带宽。

## 代码数据为什么能提升推理

这是近年最重要的发现之一（Codex、Code Llama、以及后续多篇论文）：

**加入代码数据能显著提升逻辑推理能力，即使目标是自然语言任务。**

**可能的原因**：
1. 代码有严格的**语法结构与层级依赖**，训练模型学习长程结构关系；
2. 代码执行有**确定性结果**，提供了"因果推理"的监督信号；
3. 代码中的**注释与自然语言**形成对照，强化语义对齐；
4. 代码天然要求**精确性**（差一个字符就报错），减少模糊表达。

**实测**：PaLM、LLaMA 系列都在配比中加入 4%~10% 的代码数据。

## ① 正文提取

**为什么难**：网页结构千差万别，正文可能藏在任何标签里。

**主流工具**：
- **trafilatura**（推荐）：专为语料构建设计，准确率高；
- **readability-lxml**：浏览器「阅读模式」的算法；
- **jusText**：基于文本密度；
- **BeautifulSoup + 手写规则**：可控但维护成本高。

## 为什么去重是最划算的操作

**Lee et al. (2021) 的实测结论**：在 C4 上做模糊去重，
去掉约 25% 重复内容后，训练出的模型**效果等同于使用 4 倍数据量**。

**重复数据的三大危害**：
1. 模型在重复内容上**过度训练**，导致记忆与复述（甚至直接背诵训练数据）；
2. 浪费算力——重复 token 不提供新信息；
3. 增加隐私泄露与版权风险。

## 三层去重

| 层级 | 方法 | 抓什么 | 成本 |
| --- | --- | --- | --- |
| **URL 级** | URL 规范化 + 去重 | 同一页面多次抓取 | 极低 |
| **文档级精确** | 整篇哈希（MD5/SHA） | 完全相同的文档 | 低 |
| **段落级** | 按段落哈希 | 跨文档重复段落（转载、引用） | 中 |
| **模糊（近似）** | MinHash + LSH | 「改了几个字」的转载 | 高 |

**顺序很重要**：从便宜到贵，先精确后模糊——大部分重复能被便宜的方法干掉。

## MinHash 的核心

**问题**：如何快速判断两篇文档是否「近似重复」？

**Jaccard 相似度**：

    J(A, B) = |A ∩ B| / |A ∪ B|

其中 A、B 是文档的 **shingle 集合**（连续 k 个词组成的片段，k 通常 5 或 9）。

**直接算 Jaccard 太慢**（要比较所有 shingle）。MinHash 用**随机哈希**近似：

    对集合 S 的每个元素用哈希函数 h 求值，取最小值：
    minhash(S) = min{ h(x) : x ∈ S }

**核心定理**：

    P(minhash(A) == minhash(B)) = J(A, B)

**为什么成立**：A∪B 中哈希值最小的那个元素，
如果它同时属于 A 和 B（即在交集中），则两个集合的 minhash 相同。
而这个概率正好是 |A∩B|/|A∪B| = J(A,B)。

**所以**：用 k 个不同哈希函数得到 k 维签名，
**相同位置的比例**就是 Jaccard 的估计值。

    # 签名 A: [3, 7, 1, 9, 2]
    # 签名 B: [3, 7, 5, 9, 8]
    # 相同 3 个位置 → 估计 J ≈ 0.6
